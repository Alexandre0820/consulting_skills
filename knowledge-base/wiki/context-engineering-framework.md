# Context Engineering Framework：上下文工程框架

## 核心洞察

**来源**: Nav Toor的上下文工程文章（2026），结合OpenClaw实践
**字数**: ~4000字符
**链接**: 基于speech_context_engineering_solution.md（演讲材料）

**核心观点**:
- **Context污染**是AI Agent最脆弱、最被低估的环节
- Agent表现差，80%是context管理问题
- 好的Harness（上下文工程）让同一模型性能提升数倍

---

## 为什么上下文工程决定Agent成败？

### 现实对比

**差 Harness**:
- 上下文窗口塞满无用信息
- 历史对话无结构堆积
- 工具调用结果阻塞上下文
- 每次调用成本高、质量低

**好 Harness**:
- 上下文分层管理（短期/长期/主题）
- 主动压缩和摘要
- 关键信息结构化存储
- 按需检索，精准加载

**性能差异**: 同一模型，效果可差 5-10 倍

---

## 三层上下文架构

### 1. 短期记忆（会话内）
**容量**: ~150字符摘要
**作用**: 保持当前任务连贯性
**更新频率**: 每轮对话实时更新

**实现**:
- 用system prompt维护关键上下文
- 每N轮对话触发一次摘要
- 裁剪无关历史

### 2. 主题文件（跨会话）
**容量**: 每个主题1-3KB
**作用**: 长期知识复用
**存储**: 文件系统/向量库

**示例文件**:
- `client-x-profile.md`（客户背景）
- `project-y-decisions.md`（关键决策）
- `methodology-z-summary.md`（方法论摘要）

**使用**: 任务开始时，根据query检索相关文件注入

### 3. 原始日志（归档）
**容量**: 完整对话历史
**作用**: 审计、追溯、训练数据
**存储**: 低成本存储（S3/本地）

**访问方式**: 仅当需要时搜索（如"上周讨论的X方案"）

## 关键模式

### Pattern 1: 工具结果替换（Tool Result Replacement）

**问题**: 工具返回大量原始数据，占满上下文窗口。

**解决方案**:
```python
# 执行工具后，不保留原始输出
# 仅保留:
# - 关键指标（数值）
# - 状态（成功/失败）
# - 异常信息
# - 链接到完整日志（归档）
```

**效果**: 上下文使用减少60-80%

### Pattern 2: 自动摘要（Auto-summarization）

**触发条件**:
- 对话轮次超过阈值（如20轮）
- 上下文长度超过窗口70%

**策略**:
1. 提取关键实体、决策、结论
2. 生成结构化摘要（JSON格式）
3. 替换早期内容
4. 保留摘要引用原始日志

### Pattern 3: 主题文件热加载

**流程**:
1. 用户query到达
2. 向量搜索相关主题文件（top 3-5）
3. 将摘要+关键片段注入system prompt
4. 执行任务

**热加载不包含**: 完整文件内容，只加载精选片段

## 商业价值

### 1. 成本节约
- 上下文占用减少 → token用量下降 40-60%
- 同一模型处理更长任务 → 减少模型切换

### 2. 质量提升
- 关键信息不丢失 → Agent更"聪明"
- 减少幻觉（无关信息干扰少）
- 任务完成率提升

### 3. 可扩展性
- 支持更长、更复杂的任务
- 客户项目数量提高（每个Agent管理成本下降）
