# AI Agent范式解耦指南：后台Agent时代的稳定基础设施设计

**来源**: Dan Farrelly (CTO @Inngest) X文章分析
**整理日期**: 2026-05-10
**核心价值**: Agent基础设施的分层设计原则与范型解耦策略

---

## 🎯 核心框架

### 一、范式更替的现实

**每六个月换一次**

Agent领域范式切换时间线（2018-2026）：
1. **RAG + 向量数据库** (2023) - "这才是正确方式"
2. **ReAct工具调用** (2024 H1) - Agent有了推理和工具能力
3. **Anthropic指南 - 提示词链/编排者-工作者** (2024 H2)
4. **子Agent、MCP、CLI、沙箱** (2025 H1)
5. **后台Agent** (2025 H2-至今)

**每个阶段都有人宣称"这才是正确方式"，每个阶段在当时都是最优解，但没有一个能长期稳定。**

> 如果你的基础设施耦合到这些模式中的任何一个，你已经重建过至少两次了，而且还会再建。

### 二、框架是一张赌注

**Agent框架不是库，是赌注**

| 框架 | 押注的范式 | 现状 |
|------|-----------|------|
| LangGraph | 基于图的控制流 | 已转向"deep agents" |
| CrewAI | 角色分工模式 | 维护中 |
| AutoGen | 对话式多Agent | 微软转向MAF，AutoGen维护模式 |
| LangChain | 通用Agent框架 | 生态分裂 |

**核心问题**: 框架把自己的Agent观烙印进架构。当那个Agent观过时，框架本身成了负担。

**正确的使用方式**: 框架是工具，不是架构。把框架当架构，等于信仰某个Agent观念；把框架当工具，只是快速上手的脚手架。

### 三、Anthropic的关键洞察

2024年Anthropic Agent模式指南的核心建议：

> **"从原始LLM API开始，避免那些模糊了prompt和response的框架。关于底层运作方式的错误假设，是客户错误的最常见来源。"**

**影响**:
- 颠覆了"抽象底层是必要的"这一假设
- 强调了解prompt内容对调试和可靠性的关键性
- 导致多个框架社区出现"如何响应"的激烈讨论

### 四、问题根源：耦合

**抽象可以，耦合不行**

**好的抽象**: 将原语抽象化（步骤、重试、状态）——完全合理
**坏的耦合**: 将拓扑结构抽象掉——从框架A切换到范式B意味着重写整个Agent，而非换组件

> 重写和换组件，成本差几个数量级。

**Harness概念**: Agent逻辑应运行在稳定的执行层上，只需替换业务逻辑，无需被特定框架的流程绑定。执行层不动，Agent逻辑随时能换。

### 五、五个稳定性原语（永远不换的东西）

这些原语不编码任何Agent范式，只编码**执行保障**：

1. **持久步骤 (Persistent Steps)**
   - 执行检查点，确保中途出错不丢失进度
   - 案例: Agent跑第37步挂掉，无检查点则时间和token全损

2. **持久外部状态 (Persistent External State)**
   - 能扛住进程崩溃和部署，不只活在内存
   - 对话式Agent重启即忘，后台Agent无法接受

3. **并行工作协调 (Parallel Work Coordination)**
   - 扇出/扇入、并行工具调用、子Agent分发
   - 支持5个子Agent并发运行，前3个完成后取消另外2个

4. **事件驱动控制流 (Event-Driven Control Flow)**
   - 能暂停等待外部信号（人工审批、取消），不占连接
   - HITL场景绕不开，占用线程则成本和扩展性成噩梦

5. **结构化执行可观测性 (Structured Execution Observability)**
   - 每一步、每个决策都能检查
   - 可调试具体问题，也可看整体趋势

**ReAct循环、planning agent、多Agent分发，底层都归结为同样的`step.run()`和`step.invoke()`。这是真正的稳定层。**

### 六、后台Agent的挑战（范式已至）

从同步对话式转向异步后台Agent，基础设施需求变化：

| 维度 | 对话式Agent | 后台Agent |
|------|------------|----------|
| 运行时间 | 秒级 | 分钟到小时级（45分钟+） |
| 步数 | 10-20步 | 100+步 |
| 状态持久化 | 内存即可 | 必须跨进程、跨部署 |
| 可观测性 | 日志足够 | 需要结构化trace |
| 控制流 | 同步阻塞 | 事件驱动、可暂停 |
| 生命周期 | API请求绑定 | 需要独立调度、取消、状态查询 |

**后台Agent四必须**:
- 必须长时运行且崩后能恢复（不能依赖Lambda 5分钟超时）
- 必须多步可观测（每步LLM调用、工具调用、决策点都需trace）
- 必须事件驱动控制流（等待外部输入时不占资源）
- 必须有生命周期控制（状态查询、取消、调度、检查）

### 七、沙箱不是答案

**沙箱解决"在哪里跑"，编排解决"怎么跑"**

- 沙箱提供运行时快照（进程状态），不提供工作流快照（步骤完成情况、从哪里继续）
- 有些方案把harness状态存在沙箱文件系统，让沙箱变成"意外的编排提供商"——这是混淆，代价高
- **正确关系**: 编排层在上，管理沙箱生命周期，同时保留状态

### 八、可组合性的力量

**可组合性 = 快速迭代能力**

如果原语是可组合的，新范式只是新组合方式，不需要新基础设施。

**现有组合不足以表达的 paradigm**:
- 5子Agent并发，前3完成则cancel后2，用部分结果继续
- 每晚run eval流水线，分析Agent trace，自动更新system prompt或工具选择
- 两种提示策略并行跑同一任务，评分并记录哪个赢了，积累数据集

> **可组合性的缺口，本质上是可观测性的问题。** 能看到每一步（结构化，不只是日志），才能识别哪里有效、哪里该换。

### 九、三层架构：各安其位

```
┌─────────────────────────────────────┐
│    Agent层（流动）                   │
│  - ReAct / Planning / Multi-Agent  │  ← 每3-6个月变
│  - 应用逻辑                        │
└──────────────┬──────────────────────┘
               │ 依赖
┌──────────────▼──────────────────────┐
│    编排层（稳定）                    │
│  - 持久步骤/状态                    │
│  - 事件驱动控制流                   │  ← 多年不变
│  - 可观测性/调度                   │
└──────────────┬──────────────────────┘
               │ 调用
┌──────────────▼──────────────────────┐
│    模型层（易变）                    │
│  - LLM API选择                     │
│  - 提供商切换                      │  ← 每月可能变
└─────────────────────────────────────┘
```

**检查耦合位置的诊断方法**:
- 换模型要重写很多逻辑？ → 模型层与Agent层未分离
- 换Agent思路要改基础设施？ → Agent层与编排层未分离

**疼在哪里，就是耦合在哪里。**

## ⚠️ 风险与挑战

### 风险1：技术深度要求高

**问题**: 客户可能不理解三层架构的价值，认为"换个框架就能解决"

**缓解**:
- 用具体案例说话（"第37步挂掉损失多少token"）
- 提供POC（2周小规模PoC展示健康度审计价值）
- 建立价值量化框架（成本节约、迭代速度提升）

### 风险2：市场教育成本高

**问题**: "范式解耦"概念对多数团队太超前

**缓解**:
- 降维表达（"别让基础设施跑得比你的理解快"）
- 从痛点切入（"你的Agent换个思路就要重写吗？"）
- 提供免费健康度检查工具（简化版问卷）

### 风险3：实施周期长

**问题**: 编排层实施需2-3个月，客户希望快速见效

**缓解**:
- 分阶段交付（先做评估，再试点单个Agent，最后推广）
- 提供"快速-win"模块（如可观测性平台，2周上线）
- 强调长期ROI（避免未来重建损失）
