# Agent Context与记忆管理框架

## 概述

基于《当 AI Agent 不再是玩具：从原生 OpenClaw到DeepEye的两个月进化史》文章，整理Agent在Context、上下文、记忆管理方面的最佳实践。

## 一、Context管理：从无限膨胀到三层压缩

### 1.1 原生OpenClaw的问题
- 直接依赖Claude Code内置压缩，无结构化机制
- 长对话context爆满时，Agent开始"失忆"
- 触发高费用的context reset

### 1.2 DeepEye的三层压缩机制

| 层级 | 机制 | 特点 |
|------|------|------|
| Layer 1 Micro | 工具结果替换 | 立即生效，成本最低 |
| Layer 2 Auto | 自动摘要 | 需要kimi API key |
| Layer 3 Manual | 手动压缩 | 人工干预，质量最高 |

### 1.3 压缩触发机制
- **Micro层**：工具结果实时替换
- **Auto层**：基于阈值自动触发
- **Manual层**：人工决策，结构化摘要

### 1.4 摘要质量标准
- 结构化5节格式
- 降级兜底机制
- 阈值触发提前干预

## 二、记忆治理：从一本大书到热温冷三层

### 2.1 原生OpenClaw的问题
- 使用单一MEMORY.md文件存储所有长期记忆
- 文件过大时加载失败
- 关键信息被临时信息淹没

### 2.2 DeepEye的三层记忆体系

#### 2.2.1 热层（Hot）
- **特点**：当前会话即时记忆，内存级访问
- **生命周期**：会话结束后升温或丢弃
- **用途**：实时对话支持

#### 2.2.2 温层（Warm）
- **特点**：近期活跃记忆，文件系统存储
- **组织方式**：按主题索引，Obsidian Vault双向同步
- **用途**：近期工作支持

#### 2.2.3 冷层（Cold）
- **特点**：长期归档，自动prune
- **管理策略**：过期/低价值记忆自动清理
- **用途**：历史追溯

### 2.3 MEMORY.md索引机制
- **设计理念**：作为记忆入口文件，而非存储文件
- **实现方式**：每条记忆独立存储为.md文件
- **索引方式**：MEMORY.md只保存指向这些文件的指针

## 三、身份根基：SOUL.md写入保护

### 3.1 原生OpenClaw的问题
- 允许Agent在运行中修改核心身份文件
- 缺乏约束机制
- 可能导致身份漂移

### 3.2 DeepEye的SOUL.md保护规则

#### 3.2.1 核心规则
```
对本文件的任何修改都需要用户授权确认。静默写入严格禁止。
```

#### 3.2.2 设计原理
- **防止身份漂移**：我是谁这件事，不能由我自己在运行中随意改写
- **性能考虑**：每次写入使全局prefix cache失效，代价10-40K tokens
- **稳定性保障**：人工锁定身份根基

### 3.3 对比优势

| 维度 | 原生OpenClaw | DeepEye |
|------|--------------|---------|
| 身份修改 | 无约束 | 需用户授权 |
| 静默写入 | 允许 | 严格禁止 |
| 根基稳定性 | 可能漂移 | 人工锁定 |

## 四、连续性保障：Agent Never Stop行为纪律

### 4.1 原生OpenClaw的问题
- Agent遇到不确定性就停下来请求确认
- 在自动化流程中是致命的

### 4.2 DeepEye的核心原则

#### 4.2.1 禁止请求确认语句
- 禁用"可以帮您...吗"
- 禁用"需要我继续吗"
- 禁用"请确认"等语句

#### 4.2.2 工具优先于请求
- 遇到blocker先尝试3种工具组合
- 多阶段任务不断链
- 完成当前步骤后必须通过next_action字段延续到下一步

#### 4.2.3 完成门禁机制
- **completion_criteria**：工具验证
- **产物存在检查**：输出结果验证
- **状态字段同步**：三个状态字段同步更新

### 4.3 SR v2状态机
- **功能**：解析current_step/next_action/completion_criteria
- **超时处理**：自动patch status → awaiting_resume
- **回拉机制**：有next_action时输出回拉执行指令
- **目标**：确保多步骤任务不会因为超时或错误而永久卡住

## 五、实践建议

### 5.1 优先级排序
1. **第一步**：Guardian最小改动 - 实现R0（EACCES检测）+飞书通知
2. **第二步**：Context Compressor - 实现Layer 1 Micro，投入产出比最高
3. **第三步**：Semantic Router四池 - 需要至少20个技能积累
4. **第四步**：Reflex Fabric - 适合高频重复决策场景
5. **第五步**：WealthTeam类应用 - 先做单Agent验证

### 5.2 关键指标
- **Context爆炸风险**：通过三层压缩机制控制
- **记忆管理效率**：热温冷三层分工明确
- **身份稳定性**：SOUL.md写入保护确保根基稳固
- **任务连续性**：Agent Never Stop保证自动化流程不断链

## 六、架构设计原则

### 6.1 可观测性优先
- 每个关键路径必须有日志
- 问题还没影响用户时就已经开始处理

### 6.2 失败快于无响应
- 熔断器比超时等待更好
- 立即切换fallback，不要等到超时

### 6.3 本地优先
- SQLite本地缓存
- 静态配置
- 本地决策，减少云端依赖

### 6.4 渐进激活
- 新技能active: false
- 先在非cron session验证
- 单session测试后再推广

### 6.5 单一维护入口
- pools.json symlink
- MEMORY.md索引
- .lib/skill_index.json唯一来源

---

**核心洞见**：Agent的Context和记忆管理不是简单的存储问题，而是系统稳定性的核心。好的管理架构能够确保Agent在长期运行中保持一致性、可靠性和高效性。

**应用价值**：这套框架可以直接应用到AI咨询项目中，提升Agent的稳定性和专业性，为长期客户合作提供技术保障。
