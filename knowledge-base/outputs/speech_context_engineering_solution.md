# 上下文工程：从痛点到解决方案 - 演讲材料

## 开场白

> "从Prompt工程到Context工程再到Harness工程，行业花了三年解决'怎么往上下文里塞东西'。但真正卡住所有人的，是一个没人认真回答过的问题：怎么让上下文保持干净？"

**核心观点**：Context污染是AI Agent最脆弱的环节，也是整个体系中最被低估的问题。

## 第一部分：一个真实的痛点

### 1.1 你的Agent正在被自己的记忆淹没

**典型场景**：
1. 你让AI实现功能A
2. 完成后，想到功能B也需要改
3. B做完，又想到C
4. 三轮下来，上下文塞满A、B、C的实现细节
5. 当你让AI做D时，表现开始下降

**问题本质**：不是D很难，而是A、B、C的残留信息正在干扰D

### 1.2 Context污染的特征

| 特征 | 表现 | 危害 |
|------|------|------|
| 隐性 | 不像Bug那样报错 | 难以察觉 |
| 渐进 | 质量逐渐退化 | 不知不觉 |
| 累积 | 信息不断堆积 | 性能持续下降 |

**真实案例**：2023年11月，我在前司探索prompt workflow时第一次清晰意识到这个问题。

## 第二部分：三年搏斗历程

### 2.1 2023：意识到问题

**发现时刻**：几乎所有主流产品都不支持session分叉
- 跟AI说了100句话，想回到第50句重新来，做不到
- promptflow尝试构建workflow图，但最终失败

**核心认知**：这是一个结构性问题，不是简单的产品功能缺失

### 2.2 2025：不断回滚

**解决方案**：每完成一个需求，就把上下文回滚到干净状态
- 代码变更已经commit
- 上下文回到"白纸"状态
- 拿到代码收益，卸掉上下文包袱

**公开分享**：
- 6月：北京中关村创业大街分享
- 8月：上海AI Night沙龙，提出Context无限迭代理论

**工作流程**：需求 → AI实现 → commit → 回滚上下文 → 下一个需求

### 2.3 2025-2026：工具化探索

**第一阶段**：iterm + tmux多session并行
- F5快捷键实现一键托管
- 适合极客用户

**第二阶段**：Lovcode多面板
- 参考iterm和tmux设计
- 多面板vibe coding功能

**核心问题**：面板之间Context的隔离与继承
- 10个面板都是全新session
- 面板1的信息面板2不知道
- 多面板不是答案

## 第三部分：现有方案全景分析

### 3.1 方案一：主Agent并行

**做法**：直接在对话框里让AI同时做A、B、C

**优点**：简单直接

**代价**：需求一多就崩，认知负载指数级上升

**适用场景**：需求间高度耦合且复杂度低（如同时修改PPT字体和配色）

### 3.2 方案二：主Agent串行

**做法**：做完A，在同一个对话里接着做B，再做C

**现状**：绝大多数人的默认做法

**问题**：
- 每多一轮对话，有效注意力被稀释一分
- A的调试日志、B的错误信息，都在C执行时占据宝贵窗口
- 最危险的方案（温水煮蛙）

### 3.3 方案三：Fork / Rebase

**做法**：做完一个需求后，回滚上下文到干净检查点

**产品实现**：
- **Cursor**：真fork，独立session记录，随时切换
- **Claude Code**：/branch, /fork, /btw, /rewind命令

**cc命令体系**：
- `/rewind`：回滚到检查点，丢弃后续上下文
- `/fork`：创建独立分支，保留当前进度
- `/btw`：临时岔开话题，完成后自动回到原上下文

**优势**：代码保留，上下文重置，最接近正解

**局限**：需要手动操作，用户需要上下文元认知能力

### 3.4 方案四：子Agent

**做法**：把不同需求分发给不同Agent，独立上下文

**架构**：
- 主Agent：理解需求、拆分任务
- 子Agent：独立执行，独立上下文窗口

**优势**：
- 独立上下文，避免污染
- 并行执行，效率倍增
- 只汇报结果摘要

**局限**：
- 子Agent无法修改主Agent认知
- 任务拆分本身需要上下文
- 无法解决System Prompt膨胀问题

## 第四部分：AutoContext - 优雅的解决方案

### 4.1 核心理念

**让AI自己管理自己的上下文**，而不是依赖用户的手动操作。

**关键洞察**：既然AI已经足够聪明到能帮你写代码、做架构设计，为什么不能让它自己管理自己的上下文？

### 4.2 三层架构

#### 4.2.1 第一层：Context感知（Sense）

**自我体检**：
- 当前上下文里有多少内容与新需求相关？
- 有多少是噪声（调试日志、已解决错误）？
- 当前上下文的"信噪比"是多少？

**实现特点**：无需额外模型调用，AI本身具备判断能力

#### 4.2.2 第二层：Context决策（Decide）

**智能策略选择**：

| 信噪比 | 策略 | 用户感知 |
|--------|------|----------|
| 高（>80%） | 继续 | 完全透明 |
| 中（40-80%） | 压缩 | AI自动优化 |
| 低（<40%） | Fork | 建议新分支 |
| 极低（<10%） | 全新 | 建议新session |

**额外决策**：是否更新外部Context（CLAUDE.md、AGENTS.md）

#### 4.2.3 第三层：Context进化（Evolve）

**学习机制**：
- "这个用户经常在A类需求之后紧接着做B类需求" → 在做A时预留B相关上下文
- "这个项目的测试和实现总是成对出现" → 实现功能时主动保留测试框架上下文
- "上次在上下文达到60K tokens时发生了质量退化" → 接近阈值时主动触发压缩

**沉淀方式**：将模式写入项目配置文件，形成自进化策略

### 4.3 技术实现

#### 4.3.1 Plugin + Skill架构

**为什么需要Plugin？**
- Skill只能被手动触发（/auto-context）
- AutoContext核心价值在于自动触发
- Hook机制只能通过Plugin注册

**架构设计**：
```
lovstudio/claude-code-plugin
├── hooks/
│   ├── hooks.json              ← 注册UserPromptSubmit事件
│   └── context_sense.py        ← 检测脚本：行数/体积/冷却
└── skills/                     ← submodule → lovstudio/skills
```

#### 4.3.2 "笨脚本 + 聪明提示"哲学

**脚本只做简单的事**：
- 读transcript文件的行数和体积
- 跟阈值比较
- 注入<auto-context>提示

**让Claude做聪明的事**：
- Claude有完整上下文视野
- 最佳判断"当前上下文是否与新需求相关"
- 脚本只需要告诉它"该做这个判断了"

#### 4.3.3 冷却机制

**设计**：同一session每10条消息最多触发一次

**目的**：避免过度干预，保证用户体验

### 4.4 使用体验

#### 4.4.1 完整安装（推荐）

```bash
# 30秒上手
/plugin marketplace add lovstudio/claude-code-plugin
/plugin install lovstudio@lovstudio-claude-code-plugin
```

**效果**：
- 每次提交prompt时AutoContext自动运行
- 可随时输入/auto-context手动体检
- 完全透明，无需额外操作

#### 4.4.2 仅安装Skill（手动模式）

```bash
npx skills add lovstudio/skills --skill lovstudio:auto-context
```

**效果**：需要手动输入/auto-context触发

## 第五部分：实战演示

### 5.1 电商项目开发场景

**Round 1**：用户注册功能
- 上下文充满注册流程细节、数据库schema、密码加密方案

**Round 2**：商品列表页
- **无AutoContext**：AI带着整个注册上下文去做商品列表
- **有AutoContext**：AI评估"商品列表和注册细节无关，但共享数据库配置"
- **自动操作**：压缩上下文，保留架构信息，丢弃注册细节
- **额外收益**：发现"所有API需要统一响应格式"的约定，建议写入CLAUDE.md

**Round 3**：支付集成
- **AutoContext识别**：全新领域，涉及第三方支付SDK、安全合规
- **信噪比评估**：极低
- **建议操作**：fork新session，只携带项目架构概述和API响应格式约定

**用户体验**：整个过程中，用户只需要自然地提出需求，上下文管理完全透明

### 5.2 用户体验对比

| 场景 | 无AutoContext | 有AutoContext |
|------|---------------|---------------|
| 短对话（<40条） | 正常工作 | 完全透明，无干预 |
| 长对话但话题连贯 | 质量逐渐下降 | 检测到健康，正常工作 |
| 长对话且话题漂移 | 性能明显下降 | 建议/fork或/btw |
| 用户主动检查 | 需要手动操作 | 输入/auto-context即可 |

## 第六部分：战略意义与未来展望

### 6.1 Agent自主性质变

**从工具到协作者**：
- 不再需要用户时刻监管
- 自我调节工作状态
- 像呼吸一样自动发生

### 6.2 长程任务成为可能

**突破物理限制**：
- 上下文窗口有限，但智慧的管理让它等效无限
- 理论上可以无限期持续工作
- 真正的数字分身

### 6.3 Harness自进化

**配置文件变活**：
- CLAUDE.md、AGENTS.md不再静态
- 根据项目演进自动更新
- 经验累积决定能力边界

### 6.4 组合拳效应

**AI输出质量公式**：
```
AI输出质量 = 输入质量 × 上下文质量 × 推理深度
```

**三个工具**：
1. **/brainstorm**：提升输入质量
2. **AutoContext**：优化上下文质量
3. **/tttt**：增强推理深度

**乘法效应**：任何一项为零，结果都是零

## 结束语

> "让AI变强的方式有很多种。但让AI学会自我管理，可能是其中最被低估的一种。"

**核心洞见**：
- 不是扩展AI的边界，而是让AI自己理解并管理这个边界

- 可持续的智能，而非一次性的惊艳

**未来展望**：

- 而是通过日复一日的工程实践中，悄悄学会如何让自己变得更好
- 这可能是某种意义上的"奇点"的早期形态
