## 一、核心框架：OPC = 多Agent + 共享记忆

```
OPC（一人公司）= 一个人 + 多个Agent + Wiki共享记忆

三大支柱：
1. 多Profile → 角色分工（ Researcher/Writer/Builder/Coordinator）
2. Wiki → 共享记忆层（8层结构）
3. 分层模型 → 成本控制（主+副+本地）
```

**关键洞察**：不是一个人单打独斗，而是像管理一支小团队一样管理多个Agent。

## 二、方法论提炼

### 2.1 四角色模型

| 角色 | 职责 | 核心能力 | 替代方案 |
|------|------|---------|---------|
| **Researcher** | 事实核查 | 查资料/数据/案例 | web_search + Tavily |
| **Writer** | 表达输出 | 写文章/润色/排版 | Claude/GPT-4 Writing |
| **Builder** | 技术实现 | 写代码/配置/调试 | Claude Code/Cursor |
| **Coordinator** | 统筹协调 | 分配任务/整合结果 | 主Agent或人工 |

**为什么需要多角色**：单一Agent最大的问题 = 自己写、自己审、自己觉得没问题。多角色 = 不同视角 = 更容易发现漏洞。

---

### 2.2 Wiki八层结构

| 层级 | 内容 | 更新频率 | 访问范围 |
|------|------|---------|---------|
| L1 基础信息 | 公司背景/个人档案/联系方式 | 低频 | 全员 |
| L2 知识资产 | 方法论/框架/模板 | 中频 | 全员 |
| L3 项目历史 | 历史项目/复盘/经验教训 | 项目后 | 全员 |
| L4 客户资产 | 客户信息/需求/交付历史 | 持续 | 相关角色 |
| L5 人脉网络 | 联系人/关系/合作方 | 持续 | 相关角色 |
| L6 工作流 | SOP/流程/检查清单 | 中频 | 相关角色 |
| L7 灵感捕捉 | 碎片化想法/创意/观察 | 高频 | 个人 |
| L8 元信息 | 索引/目录/使用说明 | 低频 | 全员 |

**Wiki vs Profile边界**：
- Wiki = 长期记忆（永久，无Token限制）
- Profile = 短期上下文（会话级，有Token限制）

**核心原则**：不要让模型记住所有东西，要让模型按需读取正确的信息。

---

### 2.3 Token成本分层策略

| 层级 | 模型 | 用途 | 成本 |
|------|------|------|------|
| **主模型** | Claude/GPT-4 | 复杂推理/写作/分析 | 高 |
| **副模型** | Sonnet/GPT-3.5 | 总结/整理/归档 | 中 |
| **本地模型** | Llama/Qwen | 简单任务/分类/提取 | 低 |
| **Wiki缓存** | 静态文件 | 长期上下文 | 极低 |

**预期节省**：主+副+本地组合可降低 **40-60% Token成本**

---

### 2.4 工具分工矩阵

| 工具 | 角色 | 适用场景 |
|------|------|---------|
| **终端** | Builder/Coordinator | 搭系统/改配置/调试 |
| **Web UI** | 所有角色 | 日常协作/切换Profile |
| **Wiki** | 所有角色共享 | 长期记忆/知识资产 |

**类比**：终端 = 施工现场 | Web UI = 办公室 | Wiki = 公司文档

## 四、风险提示

- **工具依赖**：Hermes是特定平台，框架需适配其他Agent平台（OpenClaw/Claude等）
- **成本实际节省待验证**：分层策略理论上可行，实际节省数据需实测
- **管理 overhead**：多Profile协作增加了管理成本（切换/协调/整合）
- **信息孤岛风险**：Profile之间信息不互通，需要Coordinator整合
