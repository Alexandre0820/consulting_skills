深夜刷到这个帖子的时候，我正好看到 Dan Farrelly 在 X 上分享的一篇文章，标题是：后台 Agent 已经到来，而你的编排还没准备好。 我的第一反应不是"真厉害"，而是反思：我这几年到底重建过几次相关框架？

细想了一下，至少两次。RAG 流行的时候搞了向量数据库，上下文窗口一下子变大，向量数据库的地位就尴尬了。后来 Anthropic 出了那篇 Agent 模式指南，我又把之前的框架选型回炉重审了一遍。每次都觉得自己在追风口，每次都觉得下次不会再这样了。

[@djfarrelly](https://twitter.com/djfarrelly) 原文：背景 Agent 已经来了，你的编排层还没准备好

## 01. 每六个月换一次

Dan 在文章里画了一条时间线，我读完心里有点发凉。从 RAG 流行、大家开始使用向量数据库，到 ReAct 带来工具调用能力，再到上下文窗口扩大后虚拟记忆需求减弱，随后 Anthropic 的博客推动了提示词链、路由和编排者-工作者模式，接着是子 Agent、MCP、CLI 以及沙箱……现在已经进入后台 Agent 的阶段。

这条时间线每个节点我都认识。每一个都有人当时说"这才是正确方式"。

有意思的是，每个节点都是有道理的。RAG 确实解决了当时的问题，向量数据库确实是那个时间窗口里最合理的选择。ReAct 让 Agent 有了推理和工具调用的能力，这是真实的进步。Anthropic 的 orchestrator-worker 模式，解决了单 Agent 无法处理复杂任务分解的问题。没有哪一步是错的，每一步都是在现有条件下的最优解。

**但"当时最优"和"长期稳定"是两回事。每一次范式切换，都会有一批人发现自己押错了宝，然后开始重建。**

> **如果你的基础设施耦合到了这些模式中的任何一个，你已经重建过至少两次了。而且还会再建。**

我把原文那段话翻译完，盯着看了一会儿。说"还会再建"，这是经验之谈，不是吓唬人。如果后台 Agent 真的是下一个范式节点——而所有迹象都在说它是——那这一轮押错宝的代价会比之前任何一次都更高，因为后台 Agent 要求的基础设施深度比对话式 Agent 复杂得多。

## 02. 框架是一张赌注

Agent 框架不是库，是赌注。Dan 把这个说得很直接。你选 LangGraph，是在赌基于图的控制流是 Agent 的正确范式；你选 CrewAI，是在赌角色分工是正确范式；你选 AutoGen，是在赌对话式多 Agent 是正确范式。

**每个框架都把自己的 Agent 观烙印进了架构里。当那个 Agent 观过时，框架本身就变成了负担。**

他举了两个例子：LangChain 已经转向了"deep agents"，AutoGen 进入了维护模式，因为微软转向了 Microsoft Agent Framework。这两个框架都曾是大家认真用过的。

> **框架之所以流行，是因为它让开发者能快速上手 Agent 工程，对初学者尤其友好。问题出在用框架的方式上：如果你把框架当成了架构，而不是工具，那你建的是对某个 Agent 观念的信仰，不是一个可以演化的系统。**

## 03. Anthropic 那一拳

Anthropic 去年发的那篇 Agent 模式指南，我当时觉得只是参考资料，读一读就行。后来仔细想，才意识到那篇东西对整个生态的破坏力有多大。

它给的建议很直接：

> **从原始 LLM API 开始，避免那些模糊了 prompt 和 response 的框架。关于底层运作方式的错误假设，是客户错误的最常见来源。**

这话等于在说：很多框架正在帮你屏蔽掉你不应该屏蔽的东西。Anthropic 当然有自己的利益在里面，但这个判断本身是站得住脚的。

生态里好几个主流框架的核心设计思路，就是让你不用知道底层 prompt 长什么样。这个思路和 Anthropic 的建议正面冲突。那篇指南发出来之后，好几个框架的社区里都出现了一波"我们应该怎么响应"的讨论。

**更深层的影响在于大家对"抽象底层"的认知发生了变化。指南发布前，很多人认为用框架隐藏底层细节是合理甚至必要的。发布后，大家逐渐意识到，了解 prompt 的内容其实关系到后期调试和系统可靠性。这种观念的变化，带来的影响可能比指南本身更深远。**

## 04. 问题在耦合

我看到这里有点被吓到了。原来后台 Agent 这一波升级，真的不是大家随便喊口号。同步还能硬撑两下，但一转成异步，很多原来用的工程手段都不灵了。原文这段，我是反复读了两遍才真的反应过来，"崩溃"这个词，原来一点也不夸张。

Dan 把这个问题说得很清楚：**抽象没问题，问题是耦合。把原语抽象掉——步骤、重试、状态——这完全合理。但不要把拓扑结构抽象掉。**

> **从一个框架方法切换到 planning-first 循环，意味着重写整个 Agent，而不是换一个组件。**这是他说的原话。重写和换组件，成本差几个数量级。

他还在另一篇文章中提到过"**harness**"概念（这里指 Agent 的外围执行环境，不是电气上的"线束"）：Agent 逻辑应该运行在一个相对稳定的执行层上，这样只需替换业务逻辑，无需被特定框架的流程绑定。**执行层不动，Agent 逻辑随时能换。**

## 05. 五个从来不换的东西

每个范式背后，有五个原语一直都在：

**① 持久步骤** — 执行检查点，确保中途出错不会丢失进度。
**② 持久外部状态** — 能扛住进程崩溃和部署，不是只活在内存里。
**③ 并行工作协调** — 扇出/扇入、并行工具调用、子 Agent 分发。
**④ 事件驱动控制流** — 能暂停等待外部信号（人工审批、取消），不用占着连接。
**⑤ 结构化执行可观测性** — 每一步、每个决策都能检查，可以调试具体问题也可以看整体趋势。

我把这五个对照以前自己踩过的坑想了一遍。持久步骤，这个是血泪教训——Agent 跑到第 37 步挂掉，如果没有检查点，从头再来，时间和 token 全损；持久外部状态，对话式 Agent 重启一下就全忘了，后台 Agent 根本没法这么搞；事件驱动控制流，HITL（人工介入循环）是很多真实场景里绕不开的，如果要占着一根线程等人回复，成本和扩展性都是噩梦。

**这五个原语本身不编码任何 Agent 范式。它们编码的是执行保障。你用它们组合成今天需要的模式，明天换一个模式，还是同一套原语。**

ReAct 循环、planning agent、多 Agent 分发，底层都归结为同样的 `step.run()` 和 `step.invoke()` 调用。这是真正的稳定层。

## 06. 后台 Agent 已经到了

上面那些还算是"以前的问题"。Dan 说，真正的挑战正在发生：**从同步的对话式 Agent，转向异步的后台 Agent。**

以前的范式大多是同步的——API 请求发出去，要尽可能快地返回，因为用户在等着。现在不一样了：

- Agent 可以跑几分钟到几小时的长任务。
- Agent 循环横跨几百步（LLM 调用加工具调用）。
- 所有成功的应用都需要异步后台执行——任务太长了，同步体验根本撑不住。

**后台 Agent 对基础设施的要求是不一样的：**

- **长时运行要能崩后恢复**: 45 分钟的 Agent 跑不了 Lambda 5 分钟超时。不能活在单进程内存里。需要能扛住重启、部署、基础设施故障的执行保障。
- **多步可观测性**: 后台 Agent 跑了 30 分钟给出一个坏结果，你要能追踪它每一步做了什么。每次 LLM 调用、工具调用、决策点、子 Agent 分发。拼日志拼状态，不够用。
- **事件驱动控制流**: 后台 Agent 需要暂停等待外部输入——人工审批、webhook 数据、另一个 Agent 的结果——同时不能占着线程、不能挂着连接。Agent 要能睡着，能被唤醒。
- **生命周期控制**: 状态查询、取消、调度、检查。没有这些，团队就只能自己拼数据库查询和定制日志钩子——然后随着规模增长不断维护一套脆弱的系统。

## 07. 沙箱不是答案

有人可能会说：沙箱提供商不是已经解决了这个问题吗？Dan 的回答很清楚：**沙箱解决的是不同的问题。**

沙箱工作在计算层——回答的问题是"Agent 在哪里跑"。有些沙箱能暂停和恢复完整的 VM 状态，这确实很强大。但那是运行时快照，不是工作流快照。它告诉你进程在什么状态，但不告诉你哪些步骤已经完成、返回了什么、从哪里继续不用重跑已成功的步骤。

有意思的是，有些人在沙箱里跑 harness（Claude Code、OpenCode 都这么干）——把 harness 的状态存在沙箱文件系统里，让沙箱的 VM 快照变成持久化层。结果是：**沙箱提供商变成了"意外的编排提供商"**。

编排层被意外地拆散在了多个层之间，可观测性和持久化级别参差不齐。这是在走向生产的路上一个代价很高的混淆。

**两层是互补的，但混为一谈代价很高。编排层应该位于沙箱上方，管理沙箱的生命周期，同时保留状态。**

## 08. 可组合才能快速迭代

Dan 说的一个点我觉得很容易被忽略：**持久化编排不只是为了可靠性，而是为了可组合性。**

今天的范式（ReAct、planning、多 Agent）不是最终的范式。新的模型能力会催生我们现在无法预测的新架构。**如果你的原语是可组合的，新范式就只是新的组合方式，不是新的基础设施。**

当你有了 `step.run()`、`step.invoke()`、`step.waitForEvent()` 和 `step.sleep()`，你可以构建出不属于任何现有分类的东西。他举了几个例子：

- 把 5 个子 Agent 并发跑，等前 3 个完成后取消另外 2 个，用部分结果继续推进。
- 每晚跑一次 eval 流水线，分析 Agent trace，自动更新 system prompt 或工具选择。
- 用两个不同的提示词策略并行跑同一个任务，等两个都完成，评分，记录哪个赢了——随时间积累数据集。

这些模式现在还没有名字。框架很难适配这类场景，因为它们编码了固定拓扑；可组合原语没有这个问题。

**还有一个角度：拥有强编排和可观测性的团队，迭代速度更快。能看到每一步（结构化，不只是日志），才能识别哪里有效、哪里该换。可组合性的缺口，本质上是可观测性的问题。**

我觉得这是全文里被低估的一段。大家谈 Agent 工程，大多数时候谈的是"怎么让 Agent 做得更好"——更好的 prompt，更好的工具选择，更好的模型。但很少有人认真谈"我怎么知道 Agent 做得好不好"。**一旦 Agent 运行时间超过 5 分钟，没有结构化可观测性，你基本上就是在瞎飞。**

## 09. 三层，各有寿命

把这一切落回到工程实践，Dan 提出了一个三层架构：

**编排层（稳定）** — 持久执行、步骤原语、事件系统、状态管理、可观测性、调度。这是你的多年级决策，Agent 范式怎么变它都不换。

**Agent 层（流动）** — 如何组织 LLM 调用、工具使用、推理、分发。这每 3-6 个月会变一次。它之所以能快速变，是因为它只是跑在持久原语上面的应用逻辑。

**模型层（易变）** — 你调用哪个 LLM、哪个 API、哪个提供商。这每个月都在变。应该是换一行代码的事，不是换架构的事。

**三层各有自己的变化频率。弄清楚每一层的寿命，就知道该在哪里用坚固的砖，哪里用可以随时扔掉的纸板。**

这个框架也给出了一个检查问题的方式：**你现在痛苦的部分，是哪一层的问题？**

- 如果你换一个模型要重写很多逻辑，那是模型层和 Agent 层没有分开；
- 如果你换一种 Agent 思路要改基础设施，那是 Agent 层和编排层没有分开。

疼在哪里，就是耦合在哪里。

## 10. 对我们意味着什么

文章写的是工程基础设施，但我读完想的不只是代码。

我现在也没法确定自己到底该往哪押注，只能边走边看。但有一点越来越清楚：**比起放心押宝某个火得快凉得也快的框架，那些不起眼的"原语"——步骤、状态、事件、可观测性——可能才是更稳的底牌。**

我说"对我们意味着什么"，其实也不确定"我们"指的是谁。做基础设施的人，这文章是非常直接的提醒。做应用层的人，可能觉得离自己有点远——毕竟大多数人还没跑到需要 45 分钟后台 Agent 的地步。但我的感觉是，这个距离比你想象的近。六个月前，multi-agent 还是个新鲜词，现在已经是标配了。

**更具体地说，如果你现在在做 AI Agent 相关的产品：**

先问自己一个问题：**我的 Agent 逻辑和编排逻辑，有没有混在一起？** 如果你的 Agent 换个思路就要重写整个系统，那大概率是耦合了。

后台 Agent 这波不是概念，21K 浏览量说明这个话题在从业者里是真实的焦虑。45 分钟的任务、跨百步的循环、等待人工审批的异步流——这些需求已经在发生了，不是等着到来。

我自己现在也在想，以前那些"一个 API 调用搞定"的场景，有多少正在悄悄变成"跑半小时、偶尔要人介入"的后台任务。**这个变化比我想象的快。**

如果你现在正在用某个 Agent 框架，我不是说它是错的，只是值得停下来问一下：**我有没有把拓扑结构耦合进去？如果要换一种 Agent 思路，我需要改多少？** 答案是几行代码，还是整个系统？这个问题的答案，比"哪个框架更好"重要得多。

Dan 在文章最后说：**后台 Agent 不是快来了，它们已经在了。唯一的问题是，你的基础设施是否准备好让它们跑，还是你即将再建一次。** 这句话我读了两遍，然后打开了自己的代码库，开始数哪些地方有我没看清楚的耦合。

哪有什么标准答案。只能提醒自己：**别让基础设施跑得比你的理解慢太多。**
